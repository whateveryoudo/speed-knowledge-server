# 语雀权限模型理解（产品对照）

> 用途：根据语雀官方文档正文整理的产品规则理解，作为本仓库权限 V2（尤其是协作列表聚合、公开性、就高合并）的对照基准。
>
> 来源：
>
> - [语雀空间权限](https://www.yuque.com/yuque/rvzzxz/bteh5g)（三层：团队 → 知识库 → 文档）
> - [语雀权限（个人版）](https://www.yuque.com/yuque/ng1qth/gxy3gk)（两层：知识库 → 文档）
>
> 说明：官方页面内截图无法在此还原；以下仅依据正文规则。本文是产品理解，不是实现规格；实现以 `permission-architecture-v2.md` 与代码为准。

## 1. 总览：两套模型

| 场景 | 层数 | 结构 |
| --- | --- | --- |
| 个人语雀 | 2 层 | 知识库 → 文档 |
| 空间语雀 | 3 层 | 团队 → 知识库 → 文档 |

共同原则：

```text
上一级权限会影响下一级
设置好上级后，可对下级批量生效，减少重复配置
```

空间版额外强调：

```text
团队权限 → 影响知识库权限
知识库权限 → 影响文档权限
```

与本仓库归属对应关系：

| 语雀场景 | 本仓库表达 |
| --- | --- |
| 个人知识库 | `space` 类型 personal，`team_id = NULL` |
| 团队知识库 | `space` 类型 organization，`team_id` 非空 |
| 空间公共区知识库 | organization + `team_id = NULL`（语雀文档未单列「公共区」，实现上按空间成员策略处理） |

## 2. 个人版（两层）

### 2.1 结构

```text
知识库
  └── 文档
```

仅需设好知识库权限，即可对库下所有文档生效。

### 2.2 知识库公开性

| 选项 | 含义 |
| --- | --- |
| 仅协作者可访问 | 私密 |
| 互联网所有人可访问 | 任意游客可看，无需登录（官方注明仅会员可用） |

无论公开性如何：**知识库协作者始终拥有该库下所有文档权限。**

### 2.3 知识库协作者身份

三种身份：

```text
可管理 / 可编辑 / 可阅读
```

高级设置可查看各身份的具体能力明细（对应本仓库的 PermissionGroup / Ability）。

### 2.4 文档权限

```text
知识库协作者 → 一定拥有该库所有文档权限
文档单独协作者 → 仅有该文档权限，没有知识库权限
```

文档也可单独设置公开性：

```text
关闭公开分享 = 文档私密
开启公开分享 = 文档公开
```

**文档公开性可突破上级知识库：**

- 私密知识库下，可将文档设为公开
- 公开知识库下，可将文档设为私密

### 2.5 个人版 QA

| 问题 | 结论 |
| --- | --- |
| 同一知识库内，不同人访问不同文档？ | 可以。库协作者必然能看全库文档；只把人加到「文档协作者」即可按篇隔离 |

## 3. 空间版（三层）

### 3.1 结构

```text
团队
  └── 知识库
        └── 文档
```

好处：

- 团队设好权限 → 对团队下所有知识库生效
- 知识库设好权限 → 对库下所有文档生效

### 3.2 团队：公开性

- 团队默认**私密**：仅团队成员可访问
- 可开启「将团队公开给所有空间成员」：
  - 空间内所有成员可看到团队顶部模块
  - 外部联系人仍无权限
  - 非空间人员仍无权限

开启后的关键限制：

```text
若用户只是「空间成员」而非「团队成员」：
  → 看不到团队里的私密知识库
  → 只能看到团队里的公开知识库
```

### 3.3 团队：成员与身份

通过「成员 → 添加成员」加入团队，身份为：

```text
管理员 / 成员 / 只读成员
```

- 仅**团队管理员**可做团队设置变更；成员 / 只读成员不可见设置入口
- 「团队设置 → 权限」可调整各身份的具体能力
- 团队层还可统一限制下级知识库能力  
  例：关闭「可编辑 → 允许修改知识库」，则对团队下**所有知识库**生效；下级知识库高级设置中对应开关也无法再开

### 3.4 知识库：协作者（核心）

知识库协作者身份同样三种：

```text
可管理 / 可编辑 / 可阅读
```

#### 自动继承（不必重复添加）

```text
团队下的知识库，会将
  「团队管理员、团队成员、团队只读成员」
自动加为协作者
```

官方矩阵（组权限可选项）：

| 团队身份 | 知识库-可管理 | 知识库-可编辑 | 知识库-可阅读 | 无权限 |
| --- | --- | --- | --- | --- |
| 团队-管理员 | ☑️（默认，锁定） | - | - | - |
| 团队-成员 | ☑️ | ☑️（默认） | ☑️ | ☑️ |
| 团队-只读成员 | - | - | ☑️（默认） | ☑️ |

官方总结：

```text
团队管理员 → 一定有团队所有知识库的「可管理」，不可取消
团队成员   → 默认「可编辑」，可修改 / 取消（含改为无权限）
团队只读   → 默认「可阅读」，可修改 / 取消（含改为无权限）
```

上级团队若关掉某能力开关，下级知识库对应能力也无法开启。

#### 单独加人 + 就高

除默认继承外，可把某人单独加为知识库协作者，与组权限冲突时 **就高继承**。

官方例子：

```text
A 是团队成员
该知识库上「团队成员」组被设为「无权限」
仍可将 A 单独加为「可编辑」
→ A 就高为可编辑
```

#### 公开性与协作者解耦

知识库公开性决定「非协作者是否能访问」；**协作者不受公开性影响，始终有权访问。**

空间版公开性三种：

| 选项 | 含义 |
| --- | --- |
| 仅协作者可访问 | 私密知识库 |
| 空间所有成员可访问 | 空间成员可读；外部联系人 / 空间外不可 |
| 互联网所有人可访问 | 未加入空间、未登录也可访问 |

### 3.5 文档权限（空间版）

与个人版一致的核心规则：

```text
知识库协作者 → 一定拥有该库所有文档权限
文档单独协作者 → 仅文档权限，无知识库权限
```

文档可在「分享 → 公开分享」中公开给：

- 空间所有成员
- 互联网所有人

**文档公开性同样可突破上级知识库：**

- 私密库下可公开文档
- 公开库下可私密文档

### 3.6 空间版 QA

| 问题 | 结论 |
| --- | --- |
| 同库不同人不同文档？ | 同个人版：加文档协作者，不加知识库协作者 |
| 团队某库仅部分成员可访问？ | 可以。先把「团队成员组 / 只读组」设为无权限，再单独加指定人。**团队管理员无法取消**，始终可访问所有库 |
| 同为团队成员又是知识库协作者，以谁为准？ | **取最大范围（就高）** |
| 如何转让知识库？ | ① 管理员仅为团队成员：权限页提权新人后自己退出；② 自己是团队管理员：需先有新的知识库可管理者，再在团队成员页降为普通成员或退出团队 |

## 4. 对本仓库 V2 的映射结论

以下为「理解语雀后」对当前实现方向的产品对齐，便于写聚合接口与前端权限页。

### 4.1 协作列表应展示什么（不要默认展开成用户）

语雀权限页展示的是 **主体行**，不是把组成员展开成真人列表：

| 行类型 | 含义 | 本仓库对应 |
| --- | --- | --- |
| 团队角色组 | 管理员 / 成员 / 只读（自动出现） | `ResourceGrant.principal_type = team_role` |
| 单独用户协作者 | 手动添加的人 | `principal_type = user` |
| （可选）待处理邀请 / 申请 | 未生效授权 | Invitation / AccessRequest，非 Grant |

个人知识库没有团队角色组，主要是 `user`（及若有空间角色策略时的 `space_role`）。

### 4.2 角色行可编辑性（知识库）

| 主体 | resource_role 默认 | 是否可改 | 是否可改为无权限 |
| --- | --- | --- | --- |
| 团队管理员组 | admin | **否（锁定）** | **否** |
| 团队成员组 | edit | 是 | 是 |
| 团队只读组 | read | 是 | 是 |
| 单独用户 | 邀请时指定 | 是（创建者例外见下） | 视产品定 |

### 4.3 就高（多路径取最大）

同一用户可能同时命中：

```text
team_role 组权限
+ user 直接授权
+（空间公开 / 互联网公开等 visibility 路径）
```

有效权限 = **各路径中最大者**（与语雀 QA「取最大范围」一致）。

聚合列表展示时：

- 组行展示组上的配置（含「无权限」）
- 用户行展示该用户的直接授权
- **鉴权计算**再做就高，不要把就高结果写死回组行

### 4.4 公开性（visibility）与协作者列表分离

```text
visibility_policy / 公开性
  → 决定「非协作者」能否读
协作者 / Grant
  → 决定具名主体的角色与能力
```

语雀明确：协作者不受公开性影响。本仓库列表聚合时：

- 不要用 visibility 过滤掉已有 Grant 行
- visibility 变更可能**锁定/隐藏**某些组选项（例如「仅协作者」下才允许把成员组改成无权限），这是 UI/策略约束，不是鉴权就高本身

### 4.5 创建者

语雀转让流程暗示：知识库始终需要可管理者；创建者退出需先保证仍有可管理方。

本仓库建议（与前期讨论一致）：

```text
创建者保留 user 直接 Grant（admin）
团队知识库另有 team_role(admin) → admin
个人侧不应通过「改个人 Grant / 退出协作」把创建者降权踢掉
转让 = 提权他人 + 再处理自己的身份（团队内则可能要改团队角色）
```

### 4.6 文档层（后续）

文档规则与语雀对齐点：

```text
1. 知识库有效协作者 → 隐式覆盖全部文档（不必为每篇写 Grant）
2. 文档可另有 user Grant，仅作用于该文档
3. 文档 visibility 可独立于知识库 visibility
```

当前优先落地 **知识库协作聚合**；文档公开突破与文档协作者列表可第二批。

### 4.7 明确暂缓（语雀有、本阶段可不做）

| 语雀能力 | 建议 |
| --- | --- |
| 团队「权限」页统一关掉下级知识库某 Ability | 后置；依赖团队策略下发到 PermissionGroup |
| 团队公开给空间成员后的「只见公开库」列表过滤 | 后置；属列表可见性，非 Grant 聚合核心 |
| 互联网公开 / 游客 | 按现有 visibility 能力逐步接 |
| 外部联系人 | 本仓库若无对等概念可忽略 |

## 5. 知识库协作聚合：实现 checklist（对照语雀）

实现 `GET` 协作聚合时，建议逐项对齐：

- [ ] 团队知识库返回 **3 条团队角色行**（即使某组被标为无权限，仍应展示该行以便配置）
- [ ] 团队管理员行：`resource_role=admin`，`locked=true`，不可改、不可删
- [ ] 成员 / 只读行：可改角色，允许「无权限」
- [ ] 额外 `user` Grant 单独成行；与组权限并存时列表都展示，鉴权就高
- [ ] 个人知识库：无团队角色行，以 user（及策略需要的 space_role）为主
- [ ] 创建者 user 行不可通过本接口降权或移除
- [ ] 待处理 Invitation / AccessRequest 与已生效 Grant 分开展示或明确状态字段
- [ ] 响应中带 `visibility` 及前端所需的选项锁定信息（若有），但不要用 visibility 剔除协作者行
- [ ] 文档继承、文档单独协作者、文档公开突破：本期可不进该接口，另开文档协作接口

## 6. 一句话对照

```text
语雀空间版 = 团队角色自动继承到知识库 + 可单独加人就高 + 公开性管游客
语雀个人版 = 只有知识库/文档两层，规则子集

本仓库 V2 Grant
  team_role / space_role / user
≈ 语雀的「组协作者 + 个人协作者」
PermissionGroup/Ability ≈ 高级设置里的能力开关
visibility ≈ 公开性
Invitation/AccessRequest ≈ 邀请与申请（未进协作者列表前的流程）
```
