# 专题 03：数据库迁移工程化与高并发建模哲学

> **核心目标**：搞懂物理外键与逻辑外键之争、MySQL DDL 隐式提交陷阱、Database-as-Code 规范，以及树形排序数据结构选型。

---

## 1. 外键之争：为什么现代互联网大厂严禁使用物理外键？

在大学数据库教材里，老师都教大家建表必须加 `FOREIGN KEY`；但在阿里巴巴《Java开发手册》第一条赫然写着：
> **【强制】不得使用外键与级联，一切外键概念必须在应用层（代码里）解决。**

大厂为什么普遍“抛弃”物理外键？我们来看对比：

| 维度 | 物理外键 (DB Foreign Key) | 逻辑外键 (应用层关联，推荐) |
| :--- | :--- | :--- |
| **数据一致性保证** | 数据库底层强校验（绝不漏脏数据） | 靠 Python/Java Service 代码逻辑保障 |
| **并发与死锁** | **极度容易死锁**：插入子表必锁主表，删除主表必全量扫描子表加锁 | **零额外加锁**：各表并发写入完全独立 |
| **分库分表与微服务** | **死穴**：一旦未来用户表在 A 库，知识库在 B 库，物理外键直接失效报错 | **无缝支持分布式与跨库跨服务演进** |
| **DDL 迁移重构** | **痛苦万分**：改列、改索引、删表时被 1553 约束死死卡死，脚本极度脆弱 | **轻量自由**：迁移脚本平滑执行，绝不卡壳 |

### 核心结论：保留普通索引，丢弃物理约束
- 字段照样叫 `user_id`, `document_id`；
- 普通 **B+ 树索引照样建**（加速查询）；
- **不要加物理约束**；校验数据合法性在 Service 代码里做；
- **ORM（如 SQLAlchemy）照样能用 `joinedload`、`selectinload`**（ORM 只需要知道 `primaryjoin` 条件，根本不在意底层有没有物理外键保安）。

## 2. MySQL DDL 隐式提交陷阱与 Database-as-Code

### 2.1 为什么 Alembic 报错后中途卡住，`downgrade` 会崩？
这是 MySQL 和 PostgreSQL 的重大区别：
- **PostgreSQL**：支持 **Transactional DDL**。一个迁移文件里的所有建表、删列都包裹在事务里，报错全部自动回滚，恢复如初。
- **MySQL**：所有 DDL 操作（`CREATE`, `ALTER`, `DROP`）都会触发 **隐式提交（Implicit Commit）**！
  - 跑完第 1 行 $\to$ 自动提交！
  - 跑完第 2 行 $\to$ 自动提交！
  - 第 3 行报错中断！
  - 此时，前两行的改动**已经永久留在数据库里了**！
  - 而 Alembic 的版本表 `alembic_version` **只有全跑通才会盖章**，此时版本号依然是旧的！
  - 若此时敲 `downgrade`，Alembic 会尝试去撤销第 50 行还没建出来的东西，引发连环崩溃。

### 2.2 状态漂移（Schema Drift）与防御性迁移
- **状态漂移**：因为报错，开发者登录 phpMyAdmin 手动点鼠标删了外键或加了字段。导致**本地真实数据库结构**与**迁移脚本代码**彻底脱节。
- **防范准则（Database-as-Code）**：
  1. 绝对不要在生产或共享环境通过 phpMyAdmin 手动修改表结构；
  2. 在迁移脚本中编写**防御性幂等代码**（如：先查 `information_schema` 字典表，确认存在才删，不存在就安全跳过）；
  3. 开发测试时，善用快照备份（`mysqldump` 1 秒重置），确保迁移脚本能在干净库上从头到尾无人值守一次性通过。

## 3. 结构迁移 (DDL) vs 数据迁移 (DML) 的分道扬镳

Alembic 的 `--autogenerate` **只认得表结构（DDL），完全看不懂业务数据回填（DML）**！

| 迁移类型 | 职责与举例 | 能否压平 (Squash) / 删旧版本？ |
| :--- | :--- | :--- |
| **结构迁移 (Schema Migration)** | 加字段、改长度、建索引 | **未上线前可以合并压平**，清理开发琐碎版本。 |
| **数据迁移 (Data Migration)** | 从旧权限表搬迁数据到新授权表、枚举值格式转换 | **绝对不能删！** 一删历史环境数据升级必然断代。 |

### 生产级多阶段发布法则：Expand and Contract（扩容-迁移-收缩）
当系统需要重构一个旧表字段时：
1. **Phase 1（扩容）**：发版本 A，先建新字段/新表，不删旧的；
2. **Phase 2（数据迁移）**：跑数据回填脚本，把旧数据洗入新结构；
3. **Phase 3（代码切换）**：业务代码全面改读新结构；
4. **Phase 4（收缩）**：发版本 B，将废弃的旧列和旧外键干净清理。

## 4. 树形结构与拖拽排序的架构演进

如何在数据库中高效存储并拖拽一棵有层级的树？

### 4.1 方案对比

| 存储方案 | 结构设计 | 查子树性能 | 拖拽节点开销 | 适用场景 |
| :--- | :--- | :--- | :--- | :--- |
| **邻接表 (Adjacency List)** | 仅存 `parent_id` | 差（需递归多次查询） | 极快（只改 `parent_id`） | 浅层级分类 |
| **物化路径 (Path Enumeration)** | 存 `path="/1/5/12/"` | 极高（`LIKE '/1/5/%'`） | 差（改一个父节点，所有子孙节点的 path 全要重写） | 电商面包屑导航 |
| **闭包表 (Closure Table)** | 额外建一张关系表存所有祖孙对 | 极高（两次关联） | 极差（拖拽需要大规模增删祖孙笛卡尔积） | 权限继承树 |
| **双向链表/孩子兄弟树 (语雀/本系统方案)** | `parent_id`, `prev_id`, `next_id`, `first_child_id` | **极高**（按指针在内存瞬时复原整棵树） | **$O(1)$ 常数级极速**（每次拖拽只更新 3~5 个指针！） | **现代富文本知识库目录树** |

### 4.2 排序算法的代际跨越

1. **第 1 代：连续整数（`order_index = 0, 1, 2, 3...`）**
   - 弊端：插到中间需要批量将后面的节点全部 `+1`（写放大，易死锁）。
2. **第 2 代：稀疏步长整型（Gap Ordering）**
   - 步长设为 65536，插中间直接取平均数，降维减少 90% 的批量更新。
3. **第 3 代：分数阶算法（Fractional Indexing / Lexorank）**
   - 存浮点数或变长字母串，永远只做单行更新，UUID 二级排序决胜，现代高并发协作看板（Jira、Notion、Figma）的终极标准。
