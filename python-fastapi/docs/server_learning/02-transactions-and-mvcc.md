# 专题 02：事务、隔离级别与 MVCC 快照读精析

> **核心目标**：透彻掌握数据库事务 ACID、四大隔离级别、MVCC 快照读原理，以及事务边界划分技巧。

---

## 1. 事务的 ACID 原性：不仅仅是理论八股

事务（Transaction）是数据库执行的**一组不可分割的最小操作单元**。它必须满足四大特性：

1. **原子性 (Atomicity)**：要么全部成功，要么全部失败回滚（如同转账：A扣钱成功但B加钱失败，A扣的钱必须自动撤销）。
2. **一致性 (Consistency)**：数据必须从一个合法状态流转到另一个合法状态（业务约束、外键约束、唯一性约束在事务结束后必须全部合规）。
3. **隔离性 (Isolation)**：多个并发事务同时操作时，互相不能看到彼此中间不稳定的状态。
4. **持久性 (Durability)**：一旦事务 `COMMIT` 提交，对数据的修改就是永久的，即使数据库立刻停电重启也不会丢失（底层由 Redo Log 保证）。

## 2. 并发事务引发的三大读现象（为什么需要隔离级别？）

当多个事务并发执行时，如果不做任何隔离，会出现以下三种诡异现象：

### 2.1 脏读（Dirty Read）—— 读到了“未提交的临时草稿”
- 事务 A 把余额从 100 改成 500（**还没提交**）；
- 事务 B 跑来查询，查到了 500 并按 500 去发货；
- 事务 A 突然抛出异常，**回滚**了，余额恢复成 100；
- **结果**：事务 B 凭空看了一眼压根不存在的假数据，造成严重资损！

### 2.2 不可重复读（Non-repeatable Read）—— 前后两次读同一行，“数值变了”
- 事务 A 第一次查余额：100 元；
- 事务 B 跑过来把这行余额改成 200 元，并**成功提交**；
- 事务 A 在同一个事务里再次查该行：变成了 200 元！
- **结果**：同一个事务里执行两次一模一样的查询，同一行数据的字段值居然不一样了。

### 2.3 幻读（Phantom Read）—— 前后两次范围查询，“行数多了/少了”
- 事务 A 范围查询：`SELECT COUNT(*) FROM user WHERE age > 18`，返回 10 行；
- 事务 B 插入了一条新用户 `age = 20` 并**成功提交**；
- 事务 A 再次统计：返回了 11 行！
- **结果**：就像见鬼了一样，凭空多出了一行数据（幻影行）。

## 3. SQL 标准的四大隔离级别

为了平衡“数据安全性”与“高并发性能”，数据库提供了 4 个可选挡位：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 性能开销 | 典型代表 |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **读未提交 (Read Uncommitted)** | ⚠️ 存在 | ⚠️ 存在 | ⚠️ 存在 | 最快（裸奔） | 极少在生产使用 |
| **读已提交 (Read Committed, RC)** | ✅ 杜绝 | ⚠️ 存在 | ⚠️ 存在 | 极高 | Oracle, PostgreSQL 默认 |
| **可重复读 (Repeatable Read, RR)** | ✅ 杜绝 | ✅ 杜绝 | ✅ 基本杜绝 | 高 | **MySQL (InnoDB) 默认** |
| **串行化 (Serializable)** | ✅ 杜绝 | ✅ 杜绝 | ✅ 杜绝 | 最慢（全排队） | 仅在极端对账系统使用 |

> **面试必备加分项**：标准 SQL 中可重复读（RR）是不防幻读的，但 **MySQL (InnoDB) 在 RR 级别下，通过 Next-Key Lock（记录锁 + 间隙锁）在当前读下基本杜绝了幻读！**

## 4. MVCC 多版本并发控制：为什么加了排他锁，别人看文档还能秒开？

很多人有这个困惑：
> *“我们在拖拽或者新建文档时，明明对整个知识库加了 `SELECT ... FOR UPDATE` 排他写锁，为什么其他几十个人在前端点开文档、看目录树，完全没有被卡住，瞬间就能打开？”*

答案就是：**MVCC（Multi-Version Concurrency Control）快照读机制！**

### 4.1 核心思想：读不加锁，读写不冲突
在 InnoDB 中，数据每被修改一次，旧版本的数据**不会立刻被物理覆盖**，而是存放在 **Undo Log（回滚日志）** 中形成一条“版本链”：

```
[最新数据: v3] ──roll_ptr──> [历史版本: v2] ──roll_ptr──> [历史版本: v1]
```

### 4.2 当前读 vs 快照读
- **快照读（Snapshot Read）**：
  普通的 `SELECT * FROM table;`。
  它不需要去争抢任何锁，数据库引擎会根据当前事务启动时的 **Read View（视图快照）**，直接在 Undo Log 链条上找到**在此事务开启前就已经提交的历史版本**返回！
  所以：**别人爱怎么写、加多重的排他锁，读者只管看自己的历史快照，零毫秒排队！**
- **当前读（Current Read）**：
  `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`、`INSERT`。
  这些操作必须读取并锁定数据的**最新物理版本**，因此会彼此排队。

## 5. 架构铁律：事务边界划分与“持锁时间最小化”

导致数据库生产事故的第一元凶，就是**“大事务（Long-running Transaction）”**。

### 5.1 事故代码剖析
```python
# ❌ 经典灾难案例：把慢速外部调用写进了数据库事务里
def create_article():
    db.begin() # 开启事务
    
    # 1. 插入文章，加了行锁
    db.query(Category).with_for_update().first() 
    
    # 2. 致命错误：在数据库事务里调用外部 AI 或第三方 HTTP 接口！
    # 假设此时大模型响应慢，耗时 5 秒钟
    ai_summary = call_openai_api(...) 
    
    # 3. 提交事务
    db.commit() # 锁被活活占用了 5 整秒！整张分类表被堵死崩盘！
```

### 5.2 黄金设计模式：持锁时间最小化
```python
# ✅ 优秀架构：事务与外部网络严格解耦
def create_article():
    # 阶段 1：快速完成数据库事务（仅耗时 2ms）
    db.query(Category).with_for_update().first()
    insert_article(...)
    db.commit() # ✨ 立刻提交！释放行锁！此时分类表立刻对其他人可用！

    # 阶段 2：在事务外部从容调用慢速网络服务
    try:
        call_openai_api(...) # 就算耗时 10 秒，数据库里也毫无任何锁负担
    except Exception:
        # 异步补偿或记录失败任务
        pass
```

**铁律**：  
**进入事务只做纯内存与高频 SQL 写入，做完立刻 `commit`；永远不要在任何事务体内发起 HTTP 请求、文件大上传、或者调用外部微服务！**
