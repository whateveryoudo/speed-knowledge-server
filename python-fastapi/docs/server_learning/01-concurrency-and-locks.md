# 专题 01：并发控制与锁机制完全指南

> **核心目标**：彻底理解悲观锁、乐观锁、排他锁、死锁与按序加锁，建立后端并发攻防体系。

---

## 1. 为什么需要锁？（并发的三大核心痛点）

在单线程环境下，代码一行行往下走，世界是安静的。但后端 Web 服务是**多线程/多进程/高并发**的：成百上千个用户的请求会在同一毫秒内到达。

如果没有锁，就会产生三种灾难：
1. **丢失更新（Lost Updates）**：张三和李四同时给余额充 100 元，两人同时读到余额是 100，分别加 100 写回 200，最终余额变成 200 而不是 300（其中 100 元蒸发了）。
2. **读脏数据 / 读写冲突**：一人正在修改并重排多行数据，另一人正巧读了一半，读出前言不搭后语的半截数据。
3. **指针与链表断裂**：多人同时往链表/树形结构头插或断链，指针覆盖导致数据变成孤岛隐形。

## 2. 悲观锁 vs 乐观锁（两种人生哲学）

面对并发冲突，计算机科学家提出了两种截然不同的处理哲学：

| 维度 | 悲观锁 (Pessimistic Locking) | 乐观锁 (Optimistic Locking) |
| :--- | :--- | :--- |
| **核心假设** | **“世界充满恶意”**：认为别人大概率会跟我同时修改这条数据。 | **“世界充满善意”**：认为大部分情况下不会有人跟我撞车。 |
| **操作策略** | **先拿锁，再办事**：谁要用谁先把门锁死，其他人全在门外排队。 | **不加锁，直接办事**：提交时查一下“我办事的期间有没有人动过数据”，没人动就提交，有人动了就重试。 |
| **数据库实现** | `SELECT ... FOR UPDATE` | `version` 版本号字段 / CAS (Compare and Swap) |
| **性能表现** | 写冲突激烈时依然稳定可靠；但并发高时排队延迟增加。 | 读多写少时性能极高（零锁开销）；但并发极高时大量重试导致 CPU 空转。 |
| **适用场景** | 涉及金钱库存、链表指针重排、文档树拖拽等**绝不能出错**的场景。 | 用户资料修改、点赞计数、协作文档无锁编辑。 |

### 乐观锁代码示例（版本号机制）
```sql
-- 1. 查询数据时带出 version
SELECT balance, version FROM account WHERE id = 1; -- 假设 version = 5

-- 2. 业务计算后写回，必须校验 version 是否还是 5，并且 version + 1
UPDATE account 
SET balance = balance + 100, version = version + 1 
WHERE id = 1 AND version = 5;

-- 3. 如果影响行数为 0，说明被别人抢先改过了，回滚重试！
```

## 3. 数据库底层的锁分类：排他锁 (X) vs 共享锁 (S)

在 MySQL (InnoDB) 引擎中，行锁主要有两种：

### 3.1 共享锁（Shared Lock，简称 S 锁 / 读锁）
- **语法**：`SELECT ... LOCK IN SHARE MODE;`
- **含义**：**“大家一起看，但谁也别想改”**。
- 多个事务可以同时持有同一行的 S 锁（读读互不阻塞）；
- 但只要有 S 锁在，任何人都无法申请写锁（排斥修改）。

### 3.2 排他锁（Exclusive Lock，简称 X 锁 / 写锁）
- **语法**：`SELECT ... FOR UPDATE;`（以及所有的 `INSERT`, `UPDATE`, `DELETE` 会自动加 X 锁）
- **含义**：**“老子在改，其他人滚粗”**。
- 一旦某行被加了 X 锁，其他事务**既不能加 X 锁，也不能加 S 锁**，必须阻塞排队。

> **关键提醒**：普通的 `SELECT * FROM table` **既不申请 S 锁，也不申请 X 锁**！  
> 它走的是 MySQL 的 **MVCC 快照读**，无论别人把这行加了多重的写锁，普通读依然能在 0 毫秒内瞬间读取历史快照返回（绝不卡顿）！

## 4. 死锁攻防：为什么会有死锁？怎么彻底破解？

### 4.1 死锁形成的四大必要条件（考点与架构精髓）
只要以下四个条件同时成立，就会必然发生死锁：
1. **互斥条件**：资源同一时刻只能被一个人独占；
2. **持有并等待**：手里拿着资源 A，同时还想去申请资源 B；
3. **不可剥夺**：别人手里的锁你不能强行抢过来；
4. **循环等待链（环路等待）**：$T_1$ 拿着 A 等 B，而 $T_2$ 拿着 B 等 A。

### 4.2 破解死锁的黄金法则：打破“环路等待”（按序加锁）
既然互斥是必须的，**消灭死锁唯一的数学解法就是：彻底打破第 4 条“循环等待”！**

#### 对比：有死锁风险 vs 零死锁架构
```python
# ❌ 错误做法：按操作的自然方向加锁（极易对撞死锁）
# 事务 1 (A -> B)：锁 A，再锁 B
# 事务 2 (B -> A)：锁 B，再锁 A
# 结局：张三拿着 A 等 B，李四拿着 B 等 A ──> 互相死等，死锁爆炸！

# ✅ 正确做法：按全局固定顺序加锁（Lock Ordering）
involved_ids = sorted([id_a, id_b])  # 永远排成升序！
for i in involved_ids:
    db.query(Entity).filter_by(id=i).with_for_update().first()

# 结局：无论是 A->B 还是 B->A，所有人都必须先拿 A，再拿 B！
# 张三抢到了 A，李四想先拿 A 拿不到，在门口空手排队（李四手里没有持有任何锁）！
# 循环闭环被彻底粉碎，死锁概率在数学上归零！
```

## 5. 聚合根容器锁定思想（Aggregate Root Locking）

很多初级开发者在加锁时会陷入误区：“动哪张表我就锁哪张表”。  
例如：拖拽修改 `knowledge_group_relation`，就去锁关系表。

### 为什么不能直接锁底层子表？
1. **空数据无行可锁**：若某个分组刚创建，里面一条关系记录都没有，`SELECT ... FOR UPDATE` 查出 0 行，根本加不上锁！并发插入仍然会撞车。
2. **行锁泛滥与间隙锁 (Gap Lock)**：关系表有成千上万行，批量给多行加锁极易触发数据库的间隙锁死锁。

### 解决方案：锁住“容器 / 聚合根”
- 分组与卡片：把整个分组看成一个“抽屉”。**不要去锁抽屉里的每一个小物件，直接锁住抽屉的把手（`KnowledgeGroup` 这一行）**！
- 无论抽屉里目前是空的，还是有 100 个卡片，抽屉把手永远有且仅有 1 个！
- 锁住抽屉把手，就可以在抽屉内部从容地重新排列、插入、删除，外部并发绝无法穿透。
